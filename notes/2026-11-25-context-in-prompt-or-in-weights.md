## 三、为什么值得记

1. **RAG 与微调之争的实质，是"知识变化频率 × 审计需求"的取舍，不是技术优劣。** 事实类知识变化快、要可追溯（谁批准的、哪个版本）→ 外挂+版本化检索；判断类知识变化慢、要内化（业务本体、领域直觉）→ 烤进权重。把两个问题混在一个 RAG 库里调参，怎么调都不对。

2. **"你无法微调一个你不托管的模型"让开源许可变成技术选型的一部分。** 过去选模型看跑分和价格，现在第一问是许可与部署形态：Apache 2.0 的文心 5.5 / Xing4.1 可以烤本体，闭源 API 再强也只能外挂。四家同日开源、两家选 Apache 2.0，卖的已经不是权重而是"权限"。

3. **Netflix 案例的关键不是 GraphRAG 这个词，而是"上下文有 owner、有版本、有检索路径"。** 拷贝进 prompt 的上下文注定腐化——没有主人、没有更新机制、没有反模式记录。45 份 ADR 里连"AI 应该怎么用这条决策"都写了，这是把组织知识当产品运维，而不是当文档存着。

4. **警惕演讲数字的转述损耗。** Rettori 的"5 万文档上限"出自他引用的一项 Google 研究，目前只能追到媒体转述；41% vs 5.2% 是单场演示（6 个 Agent、一次查询）而非受控实验。方向可信，数字引用时要带上限定条件。

## 五、术语卡

| 术语 | 解释 |
|---|---|
| ADR（Architecture Decision Record） | 架构决策记录：一份短文档记下某个技术决策的背景、选项、结论与被否方案。对 Agent 的价值在于它记的是"为什么"，而不是代码里能读出来的"是什么"。 |
| GraphRAG | 把代码结构、文档、决策记录组织成图再做检索增强生成，比平面向量检索多一层关系推理；Netflix 的做法是把每张图 pin 到 commit，保证"今天检索到的"就是"当时提交的"。 |
| 业务本体（Business Ontology） | 一个组织里"事情是怎么回事"的形式化描述：实体、流程、判断规则。JPMorgan 工程师主张用 RLHF 把它训进模型，而不是让模型每次去检索。 |
| LoRA | 低秩适配微调：不动原模型权重，只训练一小片附加参数，消费级硬件即可完成，是"空闲时段微调"这类玩法的技术前提。 |
| MoE 激活参数 | 稀疏混合专家模型中每个 token 实际参与计算的那部分参数（如 2800 亿总参/140 亿激活）。注意：激活少省的是算力，全部权重仍要占显存。 |
